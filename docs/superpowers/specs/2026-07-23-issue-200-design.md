# Issue #200 — Staged Settings Search

Date: 2026-07-23
Status: approved

## Why

Settings needs a click-activated search that first narrows navigation, then narrows
the selected section. The query is temporary UI state: it must not alter persisted
configuration or unexpectedly move the user to a different category while typing.

## Approved behavior

- Add `Search settings…` at the top of the settings sidebar using the shared
  search-bar component.
- Match case-insensitively across a setting's label, hint, explicit keywords, and
  category name.
- While a query is active, the sidebar contains only registry-backed categories
  with matches. Hotkeys and About are absent.
- Typing never changes the selected category. The user clicks a filtered category
  before its results are shown.
- A selected category shows only matching registry rows. Each result receives an
  accent border and background across the whole row; text fragments are unchanged.
- Clearing restores the full selected section. If a setting was used during the
  search session, its row is placed near the top. Otherwise the section and
  absolute scroll offset from before the search are restored.
- The query and all anchor bookkeeping are session-only.

## Structures and interfaces

`settings::search` owns the pure search and staged state:

- `SettingsUiState` owns the selected `SettingsSection` and `SettingsSearchState`.
- `SettingsSearchState` owns the raw query, current absolute scroll offset,
  pre-search section/offset, and latest interacted `SettingId`.
- `RestoreTarget` reports either a setting/category anchor or the saved
  section/offset when an active query becomes empty.
- `matching_settings(query, category)` and `matching_categories(query)` search the
  static registry without application state or Iced rendering.

The application update boundary receives dedicated messages for query changes,
scroll offsets, and tracked setting interactions. Their behavior lives in
`app/settings.rs`; `app/mod.rs` only delegates.

The view boundary gives the content scrollable and each registry row stable IDs.
Clearing to a setting first rebuilds the full section, then a widget-tree operation
locates the row container and scrolls the content viewport to that absolute offset.

## Touch map

- `src/settings/mod.rs` — add category labels and explicit keyword metadata.
- `src/settings/search.rs` — pure matching, staged state, and boundary tests.
- `src/app/settings.rs` — settings message handling and restoration tasks.
- `src/app/mod.rs` — replace the loose section field with `SettingsUiState` and
  delegate the small message boundary.
- `src/ui/search_bar.rs` — expose the shared widget with a settings-specific
  placeholder and stable input ID.
- `src/ui/settings/` — split the oversized settings view into focused section,
  control, shell, and scroll-operation modules before adding search rendering.
- `tests/panel_animation_config.rs` — retain the existing direct action-message
  contract.

## Iced 0.14 spike

A temporary example compiled a scrollable with:

- `Scrollable::id`;
- `Scrollable::on_scroll`, recording `Viewport::absolute_offset()`;
- `container::Container::id` for an anchor row; and
- `iced::widget::operation::scroll_to(id, AbsoluteOffset)` returned from update.

`cargo check --example issue_200_scroll_spike` passed. The example was then deleted
before implementation.

The spike confirmed that a saved offset can be restored directly. Iced has no
single public “scroll this child to top” helper, so row restoration will use a
small widget-tree operation that reads the identified container's bounds relative
to the identified scrollable's content bounds, then feeds that Y offset to the
public `scroll_to` task.

This exact lookup requires Iced's existing `advanced` feature because the public
scrollable helpers accept an offset but cannot derive one from a dynamically laid
out child. Hard-coded row offsets would fail for Library's variable-height folder
list. The advanced API remains isolated in `ui/settings/scroll.rs`; the resulting
offset is still applied through the public `scroll_to` helper.

## Invariants

1. An empty or whitespace-only query means search is inactive.
2. Starting a search snapshots the current section and absolute offset exactly
   once; later query edits and filtered-layout scroll events cannot replace them.
3. Query edits never change the selected section.
4. Search results contain registry entries only.
5. A result matches when any approved metadata field contains the trimmed query,
   case-insensitively.
6. Hotkeys and About never appear in active-search categories.
7. Only interactions performed while search is active become restore anchors; the
   most recent interaction wins.
8. Clearing after an interaction restores that setting's category and row.
9. Clearing without an interaction restores the pre-search category and offset.
10. Starting a later search cannot reuse an anchor from an earlier search.
11. Existing setting action messages remain the source of truth for changing
    configuration; tracking wraps them but does not replace or duplicate them.
12. No search or anchor state is serialized.

## Tests

- Registry search covers label, hint, keyword, category, casing, whitespace, and
  nonmatching values.
- Category search returns only categories represented by matching registry rows.
- State tests cover snapshot-once, no auto-switch, latest-anchor wins, both clear
  restoration branches, and fresh-session anchor reset.
- Application-boundary tests cover section selection, scroll bookkeeping, and
  setting-action delegation.
- Rendering internals are not tested.

## Out of scope

Shortcut-list filtering/sorting (#199), main tile sorting (#197), settings redesign,
persisted search, text-fragment highlighting, and non-registry static settings
content are not part of this issue.
